# Read-ownership GitHub retest

This evidence helper runs only on an isolated `perf/pr753-read-ownership-*` branch. It does not modify the production PR. This series compares three exact commits while dev remains frozen before #752/#751, avoiding an unrelated code confound. Pin all three full revisions in `read-ownership-revisions.json` before publishing. The runner rejects pending/moving revisions, unequal build or load-test sources, a baseline that is not an ancestor, and production differences beyond `TransportConnection.cs`.

Arms:

- `baseline`: exact frozen dev `072a3a13`, after #790 and before #752.
- `prior`: exact previously measured optimization revision `d3313638`.
- `safe`: exact independently reviewed safe-dispatch candidate descending from `d3313638`.

No production source is transplanted. Both baseline and prior must be ancestors of safe; both comparisons must have identical load-test/build inputs and only the intended production reader-file difference.

Each of six rounds uses one of all six arm permutations. Every arm runs in every position twice; every pair precedes/follows the other three times. All builds finish before measurement. Each observation runs in a fresh process. Macro workloads use two seconds of warmup and six seconds of measurement. The original micro uses 20,000 warmup operations and 1,000,000 measured operations per cell. New dispatch cells use 5,000 warmup and 10,000 measured operations per cell. No slow/error samples are selectively retried or excluded. A failed batch retains its partial artifacts but cannot produce a valid comparison.

The unchanged repository load tools run local TCP Add at concurrency 1/32/128, SharedMemory Add at 1/32, and TCP duplex streams of 256 elements at concurrency 1. They use Balanced profile, one fixed connection, a fixed 64 MiB send queue, and formal latency recording. SharedMemory bypasses the affected reader and is a noise control. The stream cell is a targeted check, not exhaustive transport/stream coverage.

An added minimal executable uses the production runtime assembly through its existing benchmark friend access. A deterministic zero-allocation fake inner reader measures sync, true suspension, and an awaiting consumer; both raw and wrapped cells are recorded. Tiered compilation is disabled only for these micro processes. Its small fixed construction-allocation probe is reported separately from steady-state read allocation. Allocation counters cannot prove reference-lifetime correctness; result/exception release and execution/synchronization context semantics require the independent regression suite.

## Dispatch/allocation extension

The original six-cell micro source is unchanged. A separate executable measures default-context ordinary async-await before completion, completion before ordinary await, a forced-asynchronous inner producer, and a publisher executing inside a Task. It separately measures captured custom SynchronizationContext and TaskScheduler, a custom publisher context, explicit late UnsafeOnCompleted registration, explicit FlowExecutionContext registration, and reentrant awaiting. Actual compiler-generated async consumers and direct continuation adapters are labeled distinctly.

Every cell has a raw inner-reader/framework control and a wrapped reader using exactly the same consumer/producer usage. Allocation uses `GC.GetTotalAllocatedBytes(precise: true)` so callback/worker-thread allocation remains included. It is process-wide evidence, not registering-thread-only evidence. All reads, result consumptions, advances, consumer completions and registered notifications must match the planned operation count; callbacks must drain before the endpoint. A bounded synchronous end-of-cell ThreadPool quiescence fence requires two empty/inactive samples separated by Thread.Yield. Its duration is recorded separately and remains included in elapsed/allocation/CPU measurement; new dispatch timing includes coordination, framework work and drain, not pure reader latency. No token is queried or consumed again after GetResult. Total async consumer and framework allocation can remain positive even when the wrapper's incremental allocation is zero. The report retains each within-process wrapped-minus-raw allocation point, including negative counter noise; it does not subtract raw latency or filter samples.

Late registration occurs after completion but before consuming the live result. Completed-before-ordinary-await is a separate case. A dedicated final backlog process temporarily caps only its own ThreadPool at one worker, occupies that worker, then registers late notifications while legally polling/consuming/rearming. No notification may run before release, every callback must drain after release, and original pool limits must be restored. This isolates cached-notification exhaustion cost from ordinary-await claims and prevents its pool setup affecting other cells. Pool/context/scheduler fixture setup is excluded from measured counters; only reader construction has a separate allocation probe. Backlog is a bounded burst/exhaustion experiment: the warmup burst has 5,000 notifications and the measured burst has 10,000. Queue-capacity growth may therefore remain in measured allocation, in both raw and wrapped controls; this is not a pure steady-state ordinary-await rate. The safe implementation's private forced-async selector is not patched into old sources; forced-async comparability uses the same external inner-producer behavior for every exact arm.

Dispatch and backlog each use all six arm permutations, as independent scenarios. The nine scenarios produce 162 indexed JSON/process-log pairs, including 108 unchanged macro stages. The process-wide dispatch rows are descriptive allocation evidence and cannot themselves prove consumer-exception containment; independent source regression/subprocess tests are the correctness gate.

Artifacts include immutable revisions, exact-arm clean-source diffs and provenance, copied runtime DLL identity, build logs, exact command and order, machine/.NET data, per-observation JSON and logs, descriptive means/medians/stdev/ranges, and within-round paired differences. Load JSON contains stage summaries, not every individual latency sample. CPU/allocation/GC are combined client/server/harness process metrics and include the bounded drain of measured operations. GC/1M RPC normalizes for differing completed work. Per-stage p99 values are never pooled into an overall p99.

The zero-failure gate applies only to measured stages. Existing load tools discard warmup outcomes, so this report does not assert zero warmup failures.

The six-round series is descriptive evidence on one hosted runner. It cannot reproduce or be directly compared with historical Apple M4 measurements, establish statistical equivalence, or independently justify a production Go decision. The previous local historical raw files are not inputs to this run.
