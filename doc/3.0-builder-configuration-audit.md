# #801: 3.0 Client/Server Builder configuration effectiveness audit

**Integration base:** dev at `3332559cf4db455e0249448cf16ad43f4fc36564`.
The original review used `aaedfc3f80e8fc00c504a2018577218f224ec3c3`;
the later Hosting corrections below are now included in the integration base.
This targeted audit follows the runtime *effect* of selected public
`Use*`/`Configure*` methods, rather than treating missing in-repository callers
as proof that an API has no effect. It is not a complete Builder API audit.

## Result and rule

The old endpoint `UseCodec<T>`, `UseSerializer`, standalone
`SharpLinkRuntimeContextBuilder.AddCodec<T>` and `UseCodecResolver` are
retired from the 3.0 production surface. The generated Contract-owned Codec
graph is fixed by generated manifests, `[RpcCodec]` /
`[RpcCodecImplementation]`, Adapter/Route and CodecHash. It is not
affected by runtime endpoint callback injection. The test project's
`TestOnlyCodecBuilderExtensions.AddCodec` is intentionally compiled **only**
into UnitTests/Benchmarks, not shipped as a public NuGet API.

The following configuration entry points **must be retained**, even where
the old semantic index recorded no direct in-repo call. Each has a real
materialized consumer, not a decorative compatibility shim:

| Public configuration | Write → compile/freeze → actual read/effect | Audit outcome |
| --- | --- | --- |
| Client `UseBufferWriterPool` | Client Builder → RuntimeContextBuilder.ConfigureBufferPool → RuntimeContextBuildPlan → SharpLinkBufferWriterPool.InitialCapacity → RpcSession.RentFrameWriter | **Keep**; directly tested after Build |
| Server `UseBufferWriterPool` | Server Builder → RuntimeContextBuilder.ConfigureBufferPool → RuntimeContextBuildPlan → SharpLinkBufferWriterPool.Rent | **Keep**; directly tested after Build |
| Client `UseStateStoreConcurrency` | Client Builder → RuntimeContextBuilder.ConfigureStateStores → RuntimeContext.Concurrency → RpcSession.StreamManager | **Keep**; directly tested after Build |
| Server `UseStateStoreConcurrency` | Server Builder → RuntimeContextBuilder.ConfigureStateStores → RuntimeContext.Concurrency → StripedLongMap for Server call cancellation and RpcSession.StreamManager | **Keep**; directly tested after Build |
| Client/Server `UseProtocol` | Runtime Context immutable Protocol snapshot → actual RpcSession frame metadata/wire safety limits | **Keep**; directly tested after Build |
| Client/Server `UseRpcSessionFlush` | Builder options → typed BuildPlan/composition → RpcSessionCreationOptions → RpcSession._flushOptions/SendPump | **Keep** |
| Client `UseRetry` and `UseRetry(policy)` | _retryConfigured/_retryPolicy → ClientRetryPlan → real idempotent unary retry machinery | **Keep**; do not judge by lack of public call sites |
| Client `UseDnsEndpoints` | DynamicResolverTopologyDraft with SharpLinkDnsEndpointResolver → compiled topology and actual resolver execution | **Keep** |
| Client `UseRequestCompressionPolicy` | ClientBuildPlan → ClientRuntimeComposition → CompressionSendPolicyState → request send path | **Keep** |
| Server `UseResponseCompressionPolicy` | ServerBuildPlan → ServerRuntimeComposition → CompressionSendPolicyState → response send path | **Keep** |
| SharpPack Scope `Configure` | Generator SharpPackIntegration.Emitter creates configuration call against ISharpPackRpcCodecAdapterScopeConfiguration → manifest scope before Codec creation | **Keep**; source-generated dependency |
| Host `AddSharpLinkMultiClusterClient` | IServiceCollection registration → registered coordinator Builder → hosted service/accessor | **Keep**; external DI entry; repeated-registration behavior corrected by #857 |

The newly added UnitTests exercise public Builder → actual Build → actual
Runtime Context and a real pooled writer lease on **both** Client and Server,
then check that the old Codec/Serializer interception methods are still absent
even when internal instance methods are included. The positive tests verify
the materialized configuration and writer lease, not live RPC session behavior.
The existing Server authentication test is retained; the net addition is two tests.

## Subsequent Hosting corrections included in this base

The original positive configuration checks did not establish that every
Hosting configuration path was correct. Three later fixes address distinct
cases and retain their own regression coverage:

- [#857](https://github.com/SunSi12138/SharpLink/pull/857) reuses the Builder
  actually registered in DI when registrations repeat, so later configuration
  is applied. It also registers readiness independently of pre-registered
  hosted services.
- [#858](https://github.com/SunSi12138/SharpLink/pull/858) captures the anonymous
  pipe allocator from the frozen Server build transport, preserving late
  configuration and transport ownership across startup and failure.
- [#860](https://github.com/SunSi12138/SharpLink/pull/860) preserves an explicit
  application service provider; Hosting supplies its provider only as a
  fallback. Its RPC integration tests cover provider selection and ownership.

Those fixes do not replace the buffer/state-store/protocol materialization
checks or the retired Codec/Serializer method guard added by this audit.

## What is *not* proven

Absence of in-repository callers is not a public API retirement justification.
Generated calls, reflection/DI/NativeAOT, consumer packages, and package API
baseline requirements must be reviewed before deleting public config. The
original targeted pass found no additional entirely inert Codec-like Builder
method; this is not a claim that other configuration paths were defect-free,
as the Hosting corrections demonstrate. This PR removes no production API.
Full Tier A/B/C candidate reclassification remains in #801. Package, public API,
and NativeAOT checks are separate validation evidence and are not proved by
the source-consumer matrix or the new UnitTests.
