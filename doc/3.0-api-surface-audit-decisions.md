## 明确的边界原则

1. **只有真正的用户 API、配置模型、可实现的扩展 SPI 和版本化 Generated API 5** 应保留 public；`EditorBrowsable(Never)` 不是访问控制。Generator 输出必须继续跨程序集编译。
2. **尚无派生类**不是添加 `sealed` 或删除 `public` 的充分条件。检查库内继承、用户继承、DI、Hosting、ALC、Source Generator、AOT、Trim 和实际已发布 NuGet API。
3. **新增 public→internal、移除成员与 sealed 均可能是 breaking change**：每条拆成最小 PR，对 `eng/public-api/3.0.0/*.api.txt` 做定向审阅。3.0 不承诺兼容 2.x，但必须记录迁移。
4. **固定测试套件规模**的专项门禁会检查 UnitTests 计数；将边界断言纳入既有案例，不降低计数门禁阈值。
5. 同一 `dev` 合并多条 PR 后必须重新跑最新 HEAD 的 Release Gate；单条 PR 的绿色 CI 不等于最终的版本化签审。

## 留在 public 或可继承边界的明确反例

- `IClientTransportFactory`、`IServerTransportListener`、`ITransportConnection`、`IRpcCodec<T>`、Adapter/Codec factory、interceptor、authenticator、selector、retry 等：**真实外部可实现 SPI**，继续 public。
- `IRpcRuntimeContext`、`IRpcContractCodecProviderResolver`、`IRpcChannel`、Generated codec/contract manifest/descriptor、`IRpcStub` 和 `IRpcGeneratedServerBridge`：**版本化生成代码 ABI**，即便用户业务不应直接操作也不能因“仅框架使用”而 internal。
- `SharpLinkCallContextSnapshot` → `SharpLinkServerInvocationContext`、`SharpLinkAdmissionRuleOptions` → `SharpLinkPartitionAdmissionOptions` 与 `SharpLinkException` 的派生关系：不能盲目 sealed。
- 直接可供用户配置的 Client/Server/MultiCluster Fluent 入口、公开诊断快照、Metadata、Hosting/DI：维持表意清晰的 public 成员。
