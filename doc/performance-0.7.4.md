# SharpLink 0.7.4 性能报告

本文记录 payload 压缩与主动接入控制合入前的性能门禁。结论：两个扩展关闭时，普通 Unary RPC 的分配与 0.7.3 完全相同；五轮交替负载的 QPS 为基线的 99.48%，P99 为基线的 101.37%，满足 QPS ≥99%、P99 ≤105% 的门槛。

## 环境与版本

- 日期：2026-07-20（Asia/Shanghai）。
- 机器：Apple M4，10 个物理/逻辑核心，16 GiB 内存。
- 系统：macOS 26.4.1，Darwin 25.4.0，arm64。
- SDK/Runtime：.NET SDK 10.0.102，.NET 10.0.2，Arm64 RyuJIT。
- GC：Workstation GC，Interactive latency mode。
- 修改前：`e02dd874`（v0.7.3 合并提交）。
- 候选运行时代码：`40da6aeeefb114c8b1a2485eeabb0c846d89fd05`。
- 传输：本机 TCP；负载测试进程和 BenchmarkDotNet 进程均使用 Release 构建。

基线和候选分别从独立 worktree 构建并保存二进制。同机交替运行五轮；表中的中位数是五个原始值排序后的第三个值。完整 JSON、BDN 日志和报告位于 Actions 的 `sharplink-v0.7.4-performance-<sha>` artifact，本地默认位于 `artifacts/performance/v0.7.4/`。本报告中的 Gzip/Deflate 行来自最终收窄公共内置能力之前的候选实现，仅保留为历史算法对比；发布 API 只内置 Brotli，当前复现脚本也只运行 `none` 与 `brotli`。

复现入口：

未压缩 1 MiB 可压缩数据第 5 轮出现 2 次既有 SendPump 有界背压拒绝（0.11%）；按高噪声样本复跑规则，复跑为 0 failure、2061.33 QPS、7178 μs P99，表中使用复跑值，原始失败 JSON 与复跑 JSON 均保留。

不可压缩数据虽然最终按收益策略发送原始 payload，但发送前仍必须尝试候选压缩，因此大 payload 的 CPU/QPS 成本明显。特别是 1 MiB 随机数据，Brotli 约 354 QPS，而完全关闭压缩约 1983 QPS。生产配置应只为可压缩业务启用 Provider，或提高 `MinimumPayloadBytes`；回退策略避免带宽膨胀，不承诺避免压缩尝试的 CPU 成本。

Gzip/Deflate 的历史候选数据不再代表公开内置 API；发布性能决策应以 Brotli 行和当前复现脚本为准。

## 不同算法与配置的业务数据吞吐

## 有界性结论

- Admission 队列由总 call 数和 retained wire bytes 双重预留控制；deadline、调用取消、连接断开和 Draining 使用同一取消链。排队/拒绝负载没有无界内存或延迟增长。
- Partition 池没有后台回收线程；达到容量时只回收无 waiter、无 lease 且已空闲的条目，否则以 `partition_capacity` 拒绝。
- 压缩输出和解压输出均在协议上限内预先验证并有界租借；flow-control 按原始 item 长度计费。
- 未启用 compression/admission 时不创建 limiter、provider、TagList、后台任务或每调用状态。普通 RPC 只保留 session/controller 空引用分支，BDN 证明确切分配不变。
- 所有功能性、取消竞态、owner 释放、连接复用和 NativeAOT 结果由 0.7.4 Release Gate 与 PR Quick 共同门禁；本报告只记录性能证据，不用短时基准替代正确性测试。
